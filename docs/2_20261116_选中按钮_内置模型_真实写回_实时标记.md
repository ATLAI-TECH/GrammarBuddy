# 2 · 2026-11-16 · 选中按钮、内置模型、真实写回、实时标记

## 目的

用户真的开始用原型之后提了四件事，这一篇都做了：

1. 快捷键太难用 → 选中文字后直接出现按钮。
2. 单独开 LM Studio 不友好 → 模型内嵌到 App 里，LM Studio 作为备选，并支持多种接入 AI 的方法。
3. 结果「看起来没用」→ 在真实 App 里把替换跑通，并准备一份固定的测试文本，每次都用它测。
4. 像 Grammarly 那样在原位置标记错误，不需要先选中。

## 方法和结果

### 1. 选中后的按钮（`Capture/SelectionWatcher.swift`）

- 全局监听鼠标抬起：拖选或双击之后，经辅助功能接口在本机确认有选区，在鼠标旁边显示「改错 | 翻译」小按钮；点一下走和快捷键相同的流程。
- Chrome、Slack、VS Code、Word 没有便宜的办法确认选区，拖选后就显示按钮，点了才读取。
- 故意不做「选中就自动开始」：每次选中都会把文字交给模型（用 API 时发到云端并计费），在 Chrome 这类 App 里还要反复占用剪贴板。
- 结果：用户确认「这回不错」。

### 2. 内置模型和多种接入方式（`Engine/BuiltInModel.swift`、`Engine/AppleIntelligence.swift`、Kit 的 `Backends/`）

- 用 Apple 的 MLX（`mlx-swift-lm` 3.32.3，加 `swift-huggingface`、`swift-transformers`）在 App 里直接跑 Qwen3。
- 模型来源两种：一键从 Hugging Face 下载到 `~/Library/Application Support/GrammarBuddy/Models/`；如果 LM Studio 已经下载过同一份 MLX 权重，直接读它的文件夹，不再下载。
- 思考用对话模板的 `enable_thinking: false` 关掉。首次使用加载，空闲 10 分钟卸载。
- 现在的接入方式：**内置模型（默认）**、Apple Intelligence、LM Studio、Ollama、OpenAI 兼容 API（OpenAI、Gemini、OpenRouter、DeepSeek、SiliconFlow、自定义）、Anthropic Claude。
- 结果（LM Studio 不参与）：4B 冷启动约 2 秒、之后 1 秒内；14B 冷启动约 4 秒、之后约 2 秒。

### 3. 真实写回和标准测试文本（`qa/testdoc/`、`qa/realtest.sh`）

- 用户的截图暴露了根本原因：经辅助功能读到的选区一律被判成「不知道有没有格式」，于是 ⏎ 在所有 App 里都只是复制，文字从来没被改过。
- 改法：用 `AXAttributedStringForRange` 读选区的属性。字号和粗斜体一致、没有链接 / 下划线 / 上下标 → 纯文本，⏎ 直接替换；否则 ⏎ 是复制，⌘⏎ 确认后替换。
- 标准测试文本 `qa/testdoc/GrammarBuddy-test.txt`：6 段（学术英文、邮件、Slack、带错别字的中文、带 `1.400 millones` 的西语、没有错的句子），期望结果写在同目录的 README。
- `qa/realtest.sh`：在真实的 TextEdit 里打开副本，逐段「经辅助功能选中 → 改错 → 确认 ⏎ 是替换 → 按 ⏎ → 读回比对」。
- 结果：内置 14B，自动测的 5 段全部通过。**以后改读写、面板、提示词，都先跑这个脚本。**

### 4. 实时标记（`Live/LiveChecker.swift`）

- 每 0.5 秒经辅助功能读一次前台 App 里正在编辑的文本框。文字停住约 1.2 秒后，把可见范围内改动过的段落逐段交给**本机模型**检查（内置优先；永远不会自动发给 API）。
- 每处改动用 `AXBoundsForRange` 换成屏幕坐标，在一层透明、不挡鼠标的窗口里画紫色下划线。
- 点一下有下划线的词（全局鼠标监听判断点在哪个标记上），弹出卡片：原词 → 新词，「采用 / 忽略 / 这段都忽略」。采用就经辅助功能原位替换，然后重读、重新定位。
- 只显示通过全部检查的结果（没有丢词、没有换语言、没有碰保护内容），宁可少标。
- 默认关闭，在设置 → 通用或菜单栏里打开。
- 结果：标准测试文本在 TextEdit 里标出 14 处（英文三段 4 + 5 + 3，中文 2 处，西语和没有错的那句 0 处），坐标正确；采用两处后变成 12 处，其余下划线跟着移动。
- 做不到的地方：Chrome、Slack、VS Code（不对外提供文字坐标）、Word、终端、密码框。这些地方用选中后的按钮。

### 其他

- 面板里点改动没有反应：面板不是 key 窗口时第一下点击被吞掉；整块可拖动也可能把点击当成拖动。现在第一下点击先拿 key 再照常分发，只有顶栏可以拖动。
- 双击已经在运行的 App 没有任何反应：现在会打开引导或设置，启动时在屏幕下方提示「已在菜单栏运行」。

### 5. 测试（用户说「你测试吧」之后）

- `qa/realtest.sh`（选中 → 改错 → ⏎ 替换）：内置 14B，自动测的 5 段全部通过，每段 1–3 秒。
- `qa/livetest.sh`（实时标记）：新写的。打开标准文本的副本，等下划线出现，核对标记和坐标，逐个采用，再把 TextEdit 里剩下的文字读回来比对。结果：21–24 秒内标出 14 处；全部采用后剩 0 处；四段有错的都改对，西语那段和没有错的那句没被动过。
- 单元测试 86 个全部通过。
- 测试中发现并改掉的：采用一处之后整段被重新检查，同段其他下划线会消失一下，模型还会再提一批新建议（把逗号连接的两句拆开、把句首改成大写），越改越多。现在采用一处后，同段剩下的建议原样保留、位置顺移，不重新检查。

### 6. 让实时标记在 Chrome 和 Electron 类 App 里也能用（`Capture/TextGeometry.swift`）

起因：我先说「Chrome、Slack、VS Code、Word 里做不到」，用户指出 Grammarly 都能做到，并要求去查别人的做法。这句话说得太绝对了，实际是「当时的做法做不到」。

- **查到的做法**（来源见文末）：
  - Chromium / Electron 默认不对外提供辅助功能树，辅助工具要先在对方的 App 元素上设 `AXManualAccessibility`（Electron）或 `AXEnhancedUserInterface`（Chrome），树才会出现。Chromium 的 issue 里说 Grammarly 就是这么做的。
  - 这些 App 里 `AXBoundsForRange` 返回 0×0，真实位置要走 text marker：`AXTextMarkerForIndex` 或按行取 marker → `AXTextMarkerRangeForUnorderedTextMarkers` → `AXBoundsForTextMarkerRange`。
  - Grammarly 的 Mac 版 Word 插件已经停用，Word 里现在也是靠辅助功能权限。
- **在这台 Mac 上的实测**（只读探针，测试接口的 `axprobe:`）：
  - Obsidian、VS Code：开关设置成功，之前读不到任何东西，之后能读到文本框（Obsidian：124 个字符、可写、有选区），`AXBoundsForRange` 是 0×0，text marker 接口齐全，但没有 `AXTextMarkerForIndex`。
  - Chrome：设开关返回错误码，但树照样出现了；有 `AXTextMarkerForIndex`。
  - Word：焦点落在表格上，没有文字接口，没有结论。
- **实现**：前台是这类 App 时先打开开关；取位置先试 `AXBoundsForRange`，得到 0×0 就走 text marker（没有「按下标取 marker」时，先定位到行，再在行内一步步走）；位置结果按文字内容缓存，滚动或 2 秒后失效。采用时先经辅助功能替换，不成功就选中那一段再粘贴。「选中 → 改错」的读取也先试这条路，读得到就不再占用剪贴板。
- **结果**：Chrome 里的一个本地测试页（`qa/testdoc/chrome-test.html`，输入框里是标准测试文本）标出 14 处，坐标正确（换行后的词在下一行行首）；逐个采用后剩 0 处，文字全部正确。
- **还没验证**：网页里的富文本编辑框（Gmail 写信、Slack 的输入框是 contenteditable）、Obsidian / VS Code / Slack 里的实际标记和替换、Word。

### 7. Word 里的实时标记（用户：「重点是 word，先突破」）

- **调查过程**
  1. Word 的脚本接口只有「相对页面的位置」（`get range information`），没有屏幕坐标，这条路不走。
  2. 辅助功能：Word 的文档区域是 `AXLayoutArea`，默认没有任何子元素，焦点也只落在外层容器上。
  3. 搜到一个 issue（openai/codex #57049）：Word 的 `AXEnhancedUserInterface` 变成 true 之后，文档树「大幅展开，出现了文本区域和表格单元格」。
  4. 实测：设这个开关时返回错误码（-25208），但读回来是 1；**开关要一直开着**，过几秒 `AXLayoutArea` 下面出现 `AXGroup → AXGroup → AXTextArea`，有 `AXValue`（文字）、`AXBoundsForRange`（位置）、`AXSelectedTextRange`。前两次探测失败是因为看完就把开关关了。
  5. 多页文档：**每页一个 `AXTextArea`**，各自的 `AXValue` 是这一页的文字，`AXSharedCharacterRange` 给出它在全文中的位置。新开的文档要重新设一次开关才会建树。Word 报的「可见字符范围」是全文位置，不是页内位置。
- **实现**（`Capture/TextGeometry.swift` 的 `WordAX`、`Live/LiveChecker.swift`、`WordBridge.liveReplace`）
  - 从窗口往下找各页的文本区域；检查屏幕上露出最多的那一页；被分页截断的半句不查；只保留落在窗口可见范围内的标记。
  - 采用：Word 不接受经辅助功能写入，所以用脚本接口替换（页内位置 + 这一页在全文中的起点），替换前区分大小写地核对那个位置的文字，对不上就不改。
- **结果**
  - 单页文档：标出 14 处，逐个采用后剩 0 处，用 Word 的脚本接口读回全文，逐段正确。
  - 4 页文档：按屏幕上显示的页检查；在第 2 页采用一处，改在了全文里正确的位置。
- **风险**：那个 issue 里说，开着这个开关读复杂文档时 Word 偶尔会崩溃（原因没有定论）。我们只读文字、可见页和少量范围的位置，但没有在带域、脚注、表格、修订的真实论文上测过；有这些内容时页内位置和 Word 的字符位置可能对不上，这时替换前的核对会拦下来，不会改错地方。

### 8. 逐句检查，从光标处开始（用户：「太慢了，能不能一句一句，从 focus 的地方开始改」）

- 之前：一段一段、从可见范围的顶部往下，每段查完要等下一次轮询（0.5 秒），文字变化后还要等 1.2 秒。
- 现在：按句子切（`NLTokenizer`），每句单独缓存；离光标最近的句子先查，向前后扩散；一句查完立刻查下一句；刚把光标放进去时马上开始，打字时停 0.7 秒再查；改了哪句只重查哪句。
- 结果（Word，内置 14B，模型已加载）：第一批下划线 2.4 秒出现，一页 34 句 9.6 秒查完（页里有重复的句子，重复的直接用缓存，真实文档会慢一些）。
- 同时改成**默认开启**：光标进了文本框，检查就在后台自己开始。只用本机模型；内置模型已经就绪时直接用它，不依赖 LM Studio 开着。

### 9. 下划线穿透别的 App（用户发现，要求「调查清楚」）

- **现象**：Word 里有了下划线之后，把另一个 App 叠在上面，下划线还画在那个 App 上。
- **原因**
  1. 用户当时看到的，大概率是我的测试实例画的：它被钉在 Word 上（`live:app=`），不管前台是谁都继续画；而用户自己那一份 App 在我重新构建时被我关掉了，没有重新打开。
  2. 设计本身的缺陷：下划线画在一个盖住全屏、层级是 floating 的透明窗口里，它永远在所有普通窗口之上。正常模式下切到别的 App 会在半秒内收起，但没被激活的窗口盖上来、Word 自己的菜单和对话框、以及切换的那半秒，都会穿透。
- **改法**：透明窗口改成普通层级，大小就是目标窗口的大小，用 `order(.above, relativeTo: 目标窗口号)` 紧贴在目标窗口上面一层；目标窗口用 `CGWindowListCopyWindowInfo` 按进程和标记位置找；每次轮询重新贴一次（目标窗口被提到前面、移动、缩放之后跟上）。
- **验证**（测试接口 `live:z`，读系统的窗口顺序）：Word 在前台时是「下划线层 → Word → 其他」；TermBuddy 盖上来时是「TermBuddy → 下划线层 → Word」；Word 回到前台后恢复。

## 踩坑

| 坑 | 现在的做法 |
|---|---|
| 中文旁边的 `[12]` 用的是后备字体，被判成「有格式」 | 比较字号和粗斜体，不比较字体家族 |
| 辅助功能读属性的超时 0.15 秒，模型忙的时候会超时，读成「没有选区」 | 改成 0.4 秒；测试脚本遇到这种情况重试一次 |
| 内存压力「warning」就卸载模型，这台机器长期在 warning，结果模型反复重载 | 只在「critical」时卸载 |
| 测试时去操作「最前面的 App」，而用户正在用别的 App | 测试接口加 `guard:<bundle id>`，前台不是指定 App 就跳过；实时标记的测试可以直接指定后台 App 的进程 |
| 新加的源文件不在 Xcode 工程里 | 加文件后重新运行 `xcodegen generate` |
| 用了 Swift 宏的包，命令行构建被拦 | `xcodebuild` 加 `-skipMacroValidation -skipPackagePluginValidation` |
| 刚关掉的旧实例抢走了发给新实例的第一条测试命令 | 关掉后等它退出，再启动新实例 |
| 模型没加载时返回空结果，面板显示成「删除全部原文」 | 空结果不生成改动 |
| 探测 Word 时设了开关、看一眼就关掉，结论是「Word 不提供文字」 | 开关要一直开着，并且等几秒；探测结论要多试几种条件再下 |
| 重新构建前关掉了用户自己开着的那一份 App，之后忘了重新打开；测试实例又钉在 Word 上，用户看到的是测试实例的行为 | 每次构建测试完，最后一步固定是：关掉所有测试实例，重新打开用户的那一份 |
| 透明窗口用 floating 层级，盖在所有 App 上 | 贴在目标窗口上面一层，见第 9 节 |
| 同一个 14B 模型被加载了不止一份（测试实例、用户自己开着的那一份、LM Studio），24 GB 内存不够，一段要 76–91 秒 | 测试前关掉其他实例、卸载 LM Studio 里的模型。产品上还要处理：同一时间只应有一个引擎在内存里 |

## 经验

0. **「做不到」之前先去查别人怎么做的，再实测。** 这次从「做不到」到 Chrome 里跑通，只隔了一次搜索和一个只读探针。设计稿里其实早就把 `AXManualAccessibility` 列成了要验证的项目，只是一直没测。

1. **用户用一分钟发现的问题，比模拟评审一轮还准。**「⏎ 永远是复制」这个让产品没用的 bug，五个虚拟用户都因为测试环境是模拟的而没碰到。真实 App 里的测试不能省。
2. **固定一份测试文本，每次都跑。** 有了 `realtest.sh` 之后，每个修复都能在一分钟内确认有没有真的改到 TextEdit 里的文字。
3. **设计稿里写的「不做」可以被用户推翻，但推翻时要把代价说清楚。** 实时标记原来是「不做」，现在做了，同时写明它在哪些 App 里做不到、为什么只用本机模型。
4. **「保守的默认值」叠在一起会让功能失效。**「不知道有没有格式就按有格式处理」单看是对的，但读取代码从来不回答「有没有格式」，于是每次都走最保守的那条路。
5. **内嵌依赖之前先看本机已经有什么。** LM Studio 下载的就是 MLX 权重，直接读，省掉 8 GB 的下载。

## 没有验证的

- TextEdit 以外的 App 里的真实写回和实时标记（备忘录、邮件、Pages、Safari）。
- 实时标记在长文档、滚动、多显示器、全屏下的表现；被别的窗口遮住时下划线仍会画在上面。
- 真 API；8 GB 和 16 GB 机器；内置模型放进单独进程（现在在主进程里）。
- App 调用 Word 的整条路径（需要用户点一次自动化授权）。
