# 8 · 2026-11-19 至 11-20 · 发布 0.1.0 / 0.1.1 / 0.1.2，自动更新

## 目的

1. 第一次公开发布（0.1.0）。
2. 修掉发布后用户马上碰到的问题并发 0.1.1：Word 里「插到下方」总是失败；面板底部太乱。
3. 参考 CappyBuddyPro，部署自动更新（0.1.2）。

## 方法

### 发布流程（`scripts/release.sh`）

1. XcodeGen 生成工程，`xcodebuild archive`（Release）。
2. 从归档里取出 App。归档时**手动**用 Developer ID 证书签名并加时间戳：`project.yml` 平时是自动签名，Xcode 不允许自动签名和 Developer ID 身份同时出现，所以只在发布脚本里用命令行参数覆盖。
3. 给 Sparkle 的内嵌组件重新签名（安装器、下载器、Autoupdate、Updater.app，由内到外），再给框架和 App 本身签名。Xcode 只签框架这一层，里面的组件不签，公证会拒绝。
4. 把 App 打成 zip 提交公证，通过后把票据钉到 App 上。
5. `create-dmg` 做带「拖到应用程序」的磁盘映像并签名，再公证、钉票据。
6. 用 Sparkle 的 `generate_appcast` 生成更新清单（用登录钥匙串里的 Sparkle 私钥签名），和 DMG 一起作为 GitHub Release 的附件上传。
- `SKIP_PUBLISH=1` 停在第 5 步之后；检查过再用 `PUBLISH_ONLY=1` 只做第 6 步。
- 依赖：Developer ID 证书、notarytool 的钥匙串配置（`CAPYBUDDY_NOTARY`）、`/opt/homebrew/bin` 里的 `create-dmg` 和 `gh`。

### 自动更新

- 用 Sparkle 2（和 CappyBuddyPro 一样），沿用钥匙串里同一把 Ed25519 密钥；公钥写在 Info.plist 的 `SUPublicEDKey`。
- 更新清单的位置和 CappyBuddyPro 不同：不用单独的域名和服务，清单是每个 Release 的附件，App 读 `https://github.com/ATLAI-TECH/GrammarBuddy/releases/latest/download/appcast.xml`。
- App 里：`GrammarBuddy/App/Updater.swift`；每天检查一次；菜单里「检查更新…」；设置 → 通用里两个开关（自动检查、自动下载并在退出时安装）和「现在检查」。不发送系统信息。
- 调试版可以用 `gb_feed_url` 指向别的清单，测试接口有 `update:check` / `update:state` / `update:autodownload`。

## 结果

| 版本 | 内容 | 状态 |
|---|---|---|
| 0.1.0 | 第一个公开版本 | 已发布，已公证 |
| 0.1.1 | 修复 Word「插到下方」；面板底部只留主按钮和「复制」；润色 / 语气 / 翻译只显示新文字 | 已发布，已公证 |
| 0.1.2 | 自动更新 | 已发布，已公证，带更新清单 |

每个版本都做了：`spctl` 检查（Notarized Developer ID）、深度签名校验、启动 10 秒左右无崩溃、从发布页重新下载后核对 SHA-256。

自动更新的验证：

- **本地端到端**：旧副本（0.1.1）指向本地清单，清单里是一个改了版本号（9.9.9）并用同一把密钥签名的副本。旧副本发现、下载、校验，退出后原位置变成了 9.9.9。
- **真实清单**：GitHub 上的清单返回 200，内容是 0.1.2（build 3），里面的签名用 `sign_update --verify` 对发布页下载回来的 DMG 校验通过。
- **真实清单 + 旧版本**：一个 0.1.1 的调试版读 GitHub 的清单，发现 0.1.2 并下载完成（等待退出时安装）。
- **真实清单 + 当前版本**：0.1.2 的调试版读同一份清单，结果是「已是最新」。

## 踩坑

- 第一次发布构建失败：自动签名 + Developer ID 身份冲突。改成归档时手动签名。
- `gh release create --target` 不接受短的提交号，要完整的。
- 发布后头半分钟，附件的直链会返回 404（9 个字节的「Not Found」），是同步延迟。核对下载要等一下再试，并且看文件大小，不能只看命令有没有报错。
- Sparkle 的设置存在 App 的标准偏好里，不在测试实例自己的偏好里：我在测试里打开的「自动下载」落到了用户的真实设置上，测完要删掉（已删）。
- 用户正在用的调试版如果版本号比发布版低，会被自动更新成发布版。发布后要把调试版重新构建到同一版本号。
- XcodeGen 会重新生成 `Info.plist`（被 git 跟踪），改版本号后要一起提交。
- 会话里有一条消息说「所有后台任务都结束了」，但 0.1.2 的构建其实刚开始。汇报前先查实际状态。

## 经验

- 发布分两步：先出公证好的包并检查，再公开。
- 更新功能必须端到端测一次「旧版本真的变成了新版本」，只看「发现了更新」不够。
- 清单放在 Release 附件里，不需要任何服务器，也不用往仓库里提交生成的文件。

## 还没做、已知的限制

- 0.1.0 和 0.1.1 里没有更新组件，装了这两个版本的人要手动装一次 0.1.2。
- 发布版没有测试接口，功能测试都是在调试版上做的；发布版只做了签名、公证和启动检查。
- 更新窗口（Sparkle 自带的界面）没有截图看过；「用户点安装」这条路径没有实测，测的是「自动下载、退出时安装」。
- 清单里没有带更新说明的正文，Sparkle 窗口里只会显示版本号。
- 引导流程的文字仍然在教人按全局快捷键。
