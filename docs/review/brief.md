# 设计评审：5 位模拟用户，共用说明

被评的是 GrammarBuddy 的**设计稿**，App 还没有写。你要做的是：扮演下面分配给你的人物，按设计稿的描述在脑子里一步步「使用」这个 App，完成你的人物真实会做的任务，找出设计里走不通、说不清、会让你放弃的地方。

## 要读的文件

- `docs/DESIGN.md`：被评的设计稿（每轮会更新，以文件开头的版本号为准）。
- `docs/INVESTIGATION.md`：设计之前的可行性实测。
- 第 2、3 轮还要读：上一轮你自己的报告，以及 `docs/review/round-N-fixes.md`（主持人对上一轮每条问题的处理）。

## 怎么评

1. 先写下你的人物在一个真实工作日里会用它做的 4–6 个具体任务（带具体的 App、具体的文字、具体的机器配置）。
2. 每个任务按设计稿逐步走：我按了什么 → 设计稿说会发生什么 → 这一步设计稿有没有说清楚 → 我接下来会怎么想。设计稿没写到的地方就是问题，不要替它脑补。
3. 特别留意：第一次安装到第一次成功用上要几步；出错时我看到什么；我的文字去了哪里；和我现在用的工具比，我会不会换。

## 规则

- 只写报告。不要改 `DESIGN.md`、不要改仓库里其他文件、不要写代码、不要 git commit。
- 不要启动或控制 Word、LM Studio 等任何 App，不要改系统设置。技术评审可以**只读**地查本机 SDK 头文件或接口文件来核对设计稿里的 API 说法，查了就在报告里写明查了什么、结果是什么。
- 没查证的技术判断要写明「我没验证」。
- 像真实用户一样诚实，别客气。也不要为了凑数报问题：设计稿已经明确写了「不做」并给了理由的事，除非你的人物因此完全没法用，否则不要再报。

## 报告

写到 `docs/review/round-<N>/<你的代号>.md`（中文），格式：

```
# <人物> — 设计评审 Round <N>
## 结论（评分 X/10；一句话：按这份设计做出来，我会不会用，为什么）
## 我的任务和走查过程（每个任务逐步写）
## 优点（≥3，具体到设计稿的章节）
## 问题清单
| ID | P0/P1/P2 | 设计稿位置 | 问题（在哪个任务的哪一步卡住） | 建议 |
## 上一轮问题的复查（第 2、3 轮才写：每条上一轮的问题，现在是否解决）
```

- P0 = 按设计做出来我的核心任务完不成，或者会丢数据、泄露文字；P1 = 明显影响体验或会让我放弃；P2 = 打磨。
- ID 用 `<代号首字母大写><轮次>-序号`，例如 `W1-03`。
- 最终回复只要三样：分数、最重要的 3 个问题（带 ID）、报告路径。
