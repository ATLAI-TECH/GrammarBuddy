## 七个问题的回答

1. **等多久**：实时标记测不了（没有宿主）。面板：改错 2–3 秒，润色 / 语气 3–4 秒，AI 翻译 3–7 秒。不觉得慢。计时文字「Waiting for the model… 0 s」是好的反馈。
2. **标得对不对**（面板里的改错，用的是同一份提示词）：标出来的 8 处全对，没有把对的改错，没有碰 `Notula`、`2.0`、`14h30`、人名。但漏得不少，见下一节。
3. **键盘流程**：实测不了，按代码评，见「对卡片设计的评审」。结论是 ⏎ 不该是采用键，我要 ⇥。
4. **采用之后**：测不了。
5. **段落改写**：EN 润色改得好，我敢按 ⏎。法语那段润色等于改错，没有改写。差异的问题：13 处修改用逐词的红绿交织显示，读起来是 `since over the past three months`、行首孤零零一个 `. `，我是切到 Result 才读懂的。
6. **翻译并润色**：FR→EN 准确自然，数字和日期都在（`2:30 pm`、`December 12`），`valider le parcours d'inscription` 译成 `finalize the registration process` 稍松（valider 是「确认通过」，parcours 是「流程 / 用户路径」），可接受。EN→FR 是逐词直译：`Nous avons redessiné l'éditeur depuis trois mois` 把英文的错误（since three months）原样搬了过来，法语母语者不会这么写（应为 `Nous avons passé trois mois à repenser l'éditeur`）。「润色」这一步两次几乎没起作用。和系统翻译比不了（没有语言包）。
7. **整体**：面板像一个靠谱的同事，不像「坐在旁边看一眼的朋友」，因为每次都要我先选中再叫它。会让我关掉的：⏎ 被卡片吃掉一次换行，或者在 Slack 里漏出去发了一条消息，一次就够。和 Grammarly 比，少了「为什么」；和 LanguageTool 比，法语漏得多；比两者好的是文字不出本机，以及受保护内容自动撤回。

## 对「下划线 → 卡片 → ⏎ 采用并跳到下一条」的评审（读代码，没有上屏）

### 信息够不够

卡片上有：`原词 → 新词`、`3/14`、Accept / Ignore / Ignore sentence、一行按键提示。

- **没有「为什么」。** 对非母语的人这是最大的缺口。`since → for` 不告诉我原因，我下次还会错。Grammarly 给类别加一句解释，LanguageTool 给规则名。这里是逐句的模型差异，没有现成的原因，但至少可以分「拼写 / 语法 / 标点」三类并用颜色区分。
- **纯插入时没有上下文。** `removed` 为空时卡片只显示 `→ the`，下划线画在前一个词上。我看不出要插在哪。应该带上相邻的词：`editor → editor for`。
- **卡片在词的上方**，挡住上一行，而上一行是判断这条建议的上下文。理由（Word 自己的弹窗在下方）成立，但只该在 Word 里这样做。
- 「Ignore sentence」只对这次会话有效，句子一改就失效；没有「以后不要提这个词」。

### 会不会误触（按严重程度）

**a. 连按 ⏎ 时，第二下会漏进 App。** `accept()` 一开始就 `card.hide()`，下一张卡片要等异步写回和重读之后才打开（Word 里至少 250 毫秒外加脚本调用）。这段时间 `handleKey` 的 `guard let m = activeMark, card.isVisible` 不成立，返回 false，键照常进 App。⏎ ⏎ ⏎ 正是设计鼓励的节奏，所以第二下很可能变成文档里的一个换行；在 Slack、微信这类 ⏎ 即发送的地方，就是把没改完的消息发出去。

**b. 带修饰键的 ⏎ 也会被当成采用。** `case kVK_Return, kVK_ANSI_KeypadEnter where plain:` 里，Swift 的 `where` 只约束最后一个模式，所以主键盘的 ⏎ 不管有没有 ⌘ / ⌃ / ⌥ 都会采用。⇧ 本来就不在判断里，所以 ⇧⏎（聊天里的换行）也会采用。结果：卡片开着时按 ⌘⏎（Mail、Slack 的发送）会采用一条建议并把键吃掉。

**c. ⇥ 跳过的建议会绕回来。** `openNext` 和 ⇥ 的处理都是「后面没有了就回到第一条」。我用 ⇥ 跳过的那几条没有被记住，采用完最后一条后卡片自动回到我跳过的第一条，这时手上的节奏还是 ⏎。⇥ 写的是「skip」，实际是「稍后再问」。

**d. 单击就开卡片。** `clicked()` 对任何落在下划线词上（外扩 2–3 pt）的单击都打开卡片。我点进一个词是想自己改它，或者把光标放到行尾准备换行；后一种情况下接下来的 ⏎ 被卡片拿走。

**e. 卡片和选中按钮会同时出现。** 拖选在一个有下划线的词上松手：`LiveChecker.clicked`（clicks == 1）开卡片，`SelectionWatcher.mouseUp`（dragged）出按钮，两者互不知道。双击一个标错的词（最常见的「我要重打这个词」）：第一下开卡片，第二下按下时关掉，松手后出按钮，卡片闪一下。

**f. 没有「上一条」。** ⇧⇥ 和 ⇥ 一样往前走。

### 和别人的做法比

| | 出现方式 | 采用 | 说明 |
|---|---|---|---|
| Grammarly（桌面版） | 悬停下划线出卡片 | 点建议；键盘是专门的快捷键进入后 ⇥ / ⏎ | 有类别和解释；卡片在下方 |

| GrammarBuddy | 点击或 ⌃⌘J | ⏎ | 没有解释；卡片在上方 |

GrammarBuddy 的卡片是「我去找它」，更接近 LanguageTool，本身是克制的、对的。问题只在采用键选了全系统最忙的那个键。

### 选中按钮（BubbleView）

- 三个带图标和文字的按钮（Fix | Polish | Translate），**没有 Tone**，而面板有四个标签。
- Chrome、Slack、VS Code、Notion、Obsidian、Linear、微信、Edge、Arc 和 Word 里，**任何拖动或双击都会出按钮**，不管有没有选中文字。我在 Chrome 里用 Figma、拖图片、拖分栏时它都会在指针旁边出现 6 秒。
- 位置是指针右下 8 pt，正好盖住选区之后我接着要读的那一行。
- 6 秒自动消失的计时在鼠标移上去时不会停。
- 只响应鼠标。用 ⇧ + 方向键选中的人看不到它。

## 四个明确的回答

### 1. 采用键：⇥，不是 ⏎

- ⏎ 是写作里最常按的键之一，含义还随 App 变（换行 / 发送）。任何「有时候 ⏎ 不是 ⏎」的设计，出一次错用户就不再信它。上面的 a、b 说明这不是理论风险。
- ⇥ 在正文里几乎不用，而「⇥ 接受建议」已经被编辑器的内联补全教给了很大一批用户。
- 例外：光标在列表或表格里时 ⇥ 是缩进 / 换格。这时卡片上改显示 ⌃⌘J（再按一次 = 采用并到下一条），不抢 ⇥。

建议的键位：

```
⇥        采用，并打开下一条
⇧⇥       回到上一条
→ 或 ↓   跳过这一条（记住，不再绕回来）
Esc      关闭
⏎        永远交给 App（卡片同时关闭）
其他键    关闭卡片，键照常进 App
```

如果一定要保留 ⏎：至少（1）修掉 a 和 b；（2）从采用到下一张卡片出现之间，把 ⏎ 吃掉而不是放行；（3）只有 ⌃⌘J 进入的「复查模式」里 ⏎ 才采用，鼠标点开的卡片只认鼠标和 ⇥。

### 2. 卡片怎么出：点击才出（保持现状），加一个更轻的悬停层

- **光标到了就出**：不行。写作时光标一直在动，卡片会不停地弹。
- **悬停就出完整卡片**：不行。Grammarly 的悬停卡片是我关掉它的原因之一，鼠标路过正文就弹；而且这里的卡片会装按键监听，悬停触发的监听等于随机抢键。
- **建议**：悬停 400 毫秒只出一行不可点、不装按键监听的提示（`corriger → corrigé`），鼠标移开即消失；点击或 ⌃⌘J 才出带按钮的卡片。另外，光标停在有下划线的词里时，在卡片位置出一个很小的 `⇥` 标记，提示「现在按 ⌃⌘J 可以处理这一条」，但不拦任何键。
- 点击的判定要收紧：只在「单击且 300 毫秒内没有第二次按下、没有拖动」时开卡片，避免 d 和 e。

### 3. 面板和卡片会不会让人糊涂：会，主要在按键和用词上

| | 卡片 | 面板 |
|---|---|---|
| ⏎ | 采用这一条，到下一条 | 整段替换；有时是复制（翻译、数字不符时） |
| 单条取舍 | ⇥ 跳过 | 空格 / 点击撤回 |
| 用词 | Accept / Ignore | x/y accepted、replace、copy、below |
| 入口 | 点下划线、⌃⌘J | 选中按钮、⌃⌘G、⌃⌘T |

还有一个我测不了但很担心的：实时标记逐句查，面板整段查，用同一份提示词也可能给出不同的结果。我看到 5 条下划线，选中这段点 Fix，面板说 6 处或 4 处，我会觉得其中一个坏了。

我的方案是把它们讲成**同一个东西的两个大小**，共用一套键：

- 卡片 = 一条建议；面板 = 一段的全部建议。
- 两处都是 **⇥ 采用当前 / 全部，Esc 关闭，⏎ 不抢**（面板是自己的窗口，可以保留 ⏎，但提示里把 ⇥ 写在前面）。
- 卡片上加一个「这句全部 →」的入口，直接用这句已有的结果打开面板，不重新调用模型，这样两边的数目一定一致。
- 面板打开时如果选区里已经有实时标记的结果，Fix 直接用它。

```
卡片（一条）                               面板（一段）
┌───────────────────────────────────┐     ┌──────────────────────────────────────────┐
│ 语法 · 3/14                       │     │ Fix  Polish  Tone▾  Translate▾   本机 ✕  │
│ que tu  a mentionné → as mentionnés│     ├──────────────────────────────────────────┤
│ 主语是 tu；分词与前面的 que 一致   │     │ …差异…                                   │
│                                   │     │                                          │
│ [⇥ 采用]  [→ 跳过]  这句全部 ▸  ⋯ │     │ 6 处   [⇥ 替换]  ⌘C 复制  ⌥⏎ 插到下方    │
└───────────────────────────────────┘     └──────────────────────────────────────────┘
        「这句全部 ▸」───────────────────────▶ 同一份结果，不再调用模型
```

「⋯」里放：忽略这句、以后不提这个词。第三行的解释只在点「为什么？」时才去问模型，默认不显示也行，但类别（拼写 / 语法 / 标点）应该一直在。

### 4. 「翻译并润色」找得到吗：找不到

实测的三个原因：

- 它是结果下方一行 caption 字号的蓝色链接。我的 59 词邮件，对照视图里面板停在 `Best regards,`，链接在可见范围之下（`12-fr-aitrans.png`），不滚动看不到。
- 没有法语语言包时，第一屏是「Download… / Use AI translation」，这里没有它。我要先选 AI 翻译，等 3–7 秒，再去找它，再等 3–4 秒。
- 点了之后译文原地被换掉，链接变成一个灰色的「Polished translation」，不告诉我改了哪里。两次测试分别改了 0 个词和 1 个词，我无法知道它是干了活还是没干。

而且它的名字本身让人疑惑：既然有「翻译并润色」，那普通的翻译是「翻译得不好」的意思吗？

我会这样改：把它从「翻译之后的补救」变成翻译的**两种模式**，放在语言那一行，和语言选择同级；选过一次就记住。

```
┌────────────────────────────────────────────────────────────┐
│ Fix   Polish   Tone▾   Translate                  本机  ✕ │
├────────────────────────────────────────────────────────────┤
│ French ▾ → English ▾        ( 忠实 │ 地道 ✦ )              │
│                                                            │
│ Hello Camille,                                             │
│ Thank you for your feedback on the mockups. …              │
│ Could you let me know if Thursday's meeting …              │
│   └ 相比忠实译文改了 1 处：Can → Could        [看差异]     │
├────────────────────────────────────────────────────────────┤
│ 14h30 → 2:30 pm（时间写法变了，数值相同）                  │
│                         [⇥ 替换]   ⌘C 复制   ⌥⏎ 插到下方   │
└────────────────────────────────────────────────────────────┘
```

- 「忠实」= 系统翻译或直译；「地道」= 翻译并润色。分段控件永远在第一屏，不随译文长度滚走。
- 「地道」的结果下面固定一行「相比忠实译文改了 N 处」，可以展开看差异。N = 0 时直说「没有需要润色的地方」。
- 选中按钮里的 Translate 长按或旁边的小箭头直接给「地道」。
- 没有语言包时，「地道」不需要语言包，直接可用，不必先经过「Use AI translation」。

## 测不了的

- **卡片和选中按钮的真实样子和手感**：没有宿主 App，实时标记不检查 GrammarBuddy 自己的窗口，所以没有一条标记、一张卡片出现过。上面关于卡片和按钮的每一条都标了「读代码」。I7-01 尤其需要有宿主的评审实测。
- **`open:test` 测试窗口里的真实替换**：任务要求用它，但它会把 GrammarBuddy 激活到前台，和「不要把任何 App 切到前台」冲突，我按后者处理，没有运行。所以「⏎ 之后文字真的在原处变了」我没有亲眼验证，只看到 QA 模拟的写回记录。
- **系统翻译**：这台机器没有法语语言包，EN↔FR 都停在「需要下载」。所以「系统翻译 → 翻译并润色」这条设计上的主路径我走的是「AI 翻译 → 翻译并润色」。
- **语气列表的样子**：它是一个弹出层，截图是花的，看不出实际效果。
- **等待时间里的实时标记部分**（问题 1、4）。
- 第一次语气调用 12 秒无输出，可能是共用模型排队，没有复现。
