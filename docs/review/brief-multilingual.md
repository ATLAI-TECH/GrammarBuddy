# 第 4 轮：多语言评审，共用说明

这一轮和前三轮不同。前三轮评的是设计稿；这一轮评的是**模型的真实输出**，再加上设计稿里和你的语言有关的规则。

## 要读的文件

- `qa/model-eval/results/by-language/<你的语言>.md`：两个本地模型（gemma-4-e4b，约 6 GB；gemma-4-12b，约 7 GB）对同一批文字做改错、润色、换语气、翻译的真实输出，带用时。这是主要材料。
- `qa/model-eval/corpus.json`：测试用的原文和每条的考点。
- `qa/model-eval/prompts/`：这次用的提示词。
- `docs/DESIGN.md`（v4）：只需要读和语言有关的章节：§2.5 翻译、§6.1 操作要求、§6.3 输出清洗、§6.4 保护项检查、§6.5 跑偏检查、§4.2 里差异算法的那一行。

## 你要做的三件事

1. **逐条给模型输出打分**。你是这门语言的母语者和职业文字工作者。对你语言文件里的每一条、每个模型的输出，判断：
   - 该改的错改了没有（对照考点，也看考点没列出的错）。
   - 有没有改错、改坏、多改（把对的改了，或者改变了意思、语气、地区用法）。
   - 改错有没有越界成润色。
   - 翻译：准不准，自然不自然，标点和数字是不是目标语言的习惯，称谓（正式 / 非正式）合不合适。
   - 结论：这条输出能不能不看就按 ⏎ 放回去（可直接用 / 小问题 / 不能用）。
2. **比较两个模型在你的语言上的表现**，并说明：哪个模型你会推荐给用这门语言的人；哪个不该推荐；速度和质量之间怎么取舍。
3. **指出设计和提示词里对你的语言不对或缺少的地方**。例如：这门语言的排版规则、输入法、分词、差异怎么显示才看得懂、保护项检查会不会对这门语言天天误报、语料里缺了哪类典型错误。也可以提出应该加进语料的句子（给出原文和期望的结果）。

## 规则

- 只写报告。不要改任何其他文件，不要启动或控制任何 App，不要调用模型。
- 判断输出时只看文件里的真实输出，不要凭印象评价这个模型「一般会怎样」。
- 拿不准的语言判断写明「有争议」并说明两种看法。
- 诚实，别客气，也不要为了凑数挑刺。

## 报告

写到 `docs/review/round-4/<你的代号>.md`，**用中文写**（引用原文和例句时用原来的语言），格式：

```
# <人物>（<语言>）— 多语言评审 Round 4
## 结论（一句话：哪个模型在这门语言上能用，能用到什么程度）
## 逐条评分
| 条目 | 模型 | 该改的改了吗 | 改坏或多改 | 结论（可直接用 / 小问题 / 不能用） | 说明 |
## 模型排名和推荐
## 设计和提示词的问题
| ID | P0/P1/P2 | 位置（设计稿章节或提示词文件） | 问题 | 建议 |
## 建议加进语料的句子
```

- P0 = 会把错的文字写进用户的稿子而用户很难发现；P1 = 明显影响这门语言的用户；P2 = 打磨。
- ID 用 `<代号大写>4-序号`，例如 `FR4-01`。
- 最终回复只要：两个模型在你的语言上各有几条「可直接用 / 小问题 / 不能用」，最重要的 3 个问题（带 ID），报告路径。

## 关于这次测试的背景

- 机器是 Apple M5 Pro，24 GB 内存，模型经 LM Studio 运行。第三个模型（qwen 27B，约 17 GB）在这台机器上 12 分钟没有输出任何内容，已放弃，所以只有两个模型。
- 每条输出后面括号里有用时。带「thinking N chars」的表示模型在回答前自己先思考了一段，这段思考用户看不到，但要等。用时也是你评价的一部分：用户按下快捷键后要等这么久。
- 输出里如果出现原文没有的 Markdown 记号（例如给学名加上 `*…*`），也算模型的问题，请指出。
